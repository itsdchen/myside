# n1 Provisioning + Disaster Recovery Runbook

Canonical "AWS account → running publisher on ZMQ" recipe for a Hyperliquid
non-validating node box. Last refreshed 2026-06-25.

This is both:
- **First-time provisioning** for a brand-new n1 (or n2, n3, etc.)
- **Full disaster recovery** if n1 is lost (instance terminated, EBS corrupt,
  region failure, etc.) — same procedure, just done under pressure

Follow top to bottom. Each step has a verification check and points at a
concrete artifact in `overmind/studies/` to copy rather than re-derive.

For *operating* an already-provisioned box (commands, paths, troubleshooting),
see `n1_navigation_guide.md` instead. For the *why* behind the decisions
below (instance type, EIP, etc.), see `README.md`.

---

## Disaster recovery scenarios + time estimates

If something has broken, identify which scenario applies before opening a
shell. Each has different ETA:

| scenario | what's preserved | what to do | ETA to feed-back-up |
|---|---|---|---|
| **hl-node panicked / OOM'd** | Everything on EBS | hl-visor's watchdog usually relaunches; if not, `sudo systemctl restart hl-visor.service` (use script file to avoid singleton-check). | < 2 min |
| **hl-node memory bloated, not yet OOM** | Everything | Run `/usr/local/bin/hl_weekend_restart.sh --force` on n1. Daily cron will catch this normally. | < 2 min |
| **Publisher stuck (ZMQ silent but service active)** | Everything | Restart publisher: `sudo systemctl restart hl-publisher-books.service` (+ fills). Books publisher will re-bootstrap from WS, ~10 s phantom resolution. | < 1 min |
| **EIP somehow released or unassigned** | Instance, EBS, configs | Re-allocate (if old EIP is lost) and re-associate. **Notify validator operator of new IP.** Update `~/.ssh/config`. | < 5 min |
| **Instance dead but EBS intact** | Chain state, configs, software | Launch fresh instance (step 1), attach existing EBS as root, skip steps 3-12 (already installed), associate EIP, verify. | < 15 min |
| **EBS corrupt or lost** | Nothing on n1 | Full rebuild from this runbook, all steps. Chain re-sync from genesis or HL-published snapshot is the slow part. | 2-4 h |
| **Whole AWS account lost** | This runbook (in git) + AWS account `l1` credentials | New AWS account, full rebuild + redirect alerts/billing. Coordinate with validator operator for new IP whitelist. | 6-12 h |
| **Region failure (ap-northeast-1)** | Everything in git, n1 unreachable | Move to ap-northeast-3 (Osaka) or back to ap-northeast-1 when restored. New peer set means peer-network outliers for ~24 h until n1 is stable. | 2-6 h |

## 1. Launch the EC2 instance

All decisions baked in: `r6i.4xlarge`, Ubuntu 24.04, 500 GB gp3 root,
ap-northeast-1a, dedicated SG `hl-node-sg`, **no EIP** (use private IP for
fan-out; auto-assigned public IP for SSH).

```bash
# Latest 24.04 AMI
AMI=$(aws ssm get-parameter --region ap-northeast-1 \
  --name /aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id \
  --query Parameter.Value --output text)

# Security group: one-time create. Skip if `hl-node-sg` already exists.
SG_ID=$(aws ec2 create-security-group --region ap-northeast-1 \
  --vpc-id vpc-05ff5da2c2153c852 \
  --group-name hl-node-sg \
  --description "HL non-validating node" \
  --query GroupId --output text)
aws ec2 authorize-security-group-ingress --region ap-northeast-1 --group-id "$SG_ID" \
  --ip-permissions \
    'IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges=[{CidrIp=0.0.0.0/0,Description="SSH"}]' \
    'IpProtocol=tcp,FromPort=4001,ToPort=4002,IpRanges=[{CidrIp=0.0.0.0/0,Description="HL peer gossip"}]' \
    'IpProtocol=udp,FromPort=60000,ToPort=61000,IpRanges=[{CidrIp=0.0.0.0/0,Description="Mosh"}]' \
    'IpProtocol=-1,IpRanges=[{CidrIp=172.31.0.0/16,Description="Internal VPC"}]'

# Launch
INSTANCE_ID=$(aws ec2 run-instances --region ap-northeast-1 \
  --image-id "$AMI" \
  --instance-type r6i.4xlarge \
  --key-name l1_dchen \
  --subnet-id subnet-0b8aecc4285e4208e \
  --security-group-ids "$SG_ID" \
  --block-device-mappings 'DeviceName=/dev/sda1,Ebs={VolumeSize=500,VolumeType=gp3,DeleteOnTermination=true}' \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=hl-node}]' \
  --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --region ap-northeast-1 --instance-ids "$INSTANCE_ID"
aws ec2 describe-instances --region ap-northeast-1 --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].[PublicIpAddress,PrivateIpAddress]' --output text
```

**EBS throughput bump to production setting (gp3 1000 MB/s + 4000 IOPS):**

This is the E12 setting that eliminated snapshot-correlated fast stalls.
gp3 enforces a 0.25 MB/s per IOPS ratio, so 1000 MB/s requires ≥4000 IOPS.
Cost delta: ~$35/mo over the gp3 baseline.

```bash
VOL=$(aws ec2 describe-instances --region ap-northeast-1 --instance-ids "$INSTANCE_ID" \
  --query 'Reservations[0].Instances[0].BlockDeviceMappings[0].Ebs.VolumeId' --output text)
aws ec2 modify-volume --region ap-northeast-1 --volume-id "$VOL" \
  --throughput 1000 --iops 4000
```

**Verify:** `aws ec2 describe-instances` returns `running`; `nc -zv <publicIP> 22` succeeds. `aws ec2 describe-volumes --volume-ids $VOL` shows `Throughput: 1000, Iops: 4000`.

## 7. Disk retention cron

The node writes ~144 GB/day on Mainnet. The retention script gzips streaming
files >2 h old and deletes files >72 h old; for the aggressive dirs
(`replica_cmds`, `periodic_abci_states`) it drops anything >1 h.

```bash
scp overmind/studies/hl_node_mainnet_samples/hl_data_retain.sh n1:/tmp/
ssh n1 <<'EOF'
sudo install -m 755 /tmp/hl_data_retain.sh /usr/local/bin/hl_data_retain.sh
sudo mkdir -p /var/lib/hl_data_retain
sudo chown ubuntu:ubuntu /var/lib/hl_data_retain
# Cron every 10 min, ubuntu user
echo '*/10 * * * * /usr/local/bin/hl_data_retain.sh >> /var/log/hl_data_retain.log 2>&1' \
  | sudo tee /etc/cron.d/hl-data-retain >/dev/null
sudo systemctl restart cron
EOF
```

**Verify:** wait 15 min, then `ssh n1 'tail /var/log/hl_data_retain.log'` —
should show a successful run. `du -sh ~/hl/data/*` should plateau within
~3 hours of the node being live.

⚠ **Trap that bit us on n2 twice (2026-06-23 and 2026-06-26)**: the
`mkdir -p /var/lib/hl_data_retain` step is easy to skip if you
cherry-pick parts of this recipe — or if you skip step 7 entirely
when standing up a test box. Without that directory, `flock` in the
script fails silently every cron tick (cron output is suppressed).
Disk fills at ~40 GB/h and the 484 GB root is gone in ~12 h.
`replica_cmds` alone can hit 264 GB in a day.

**Always do step 7 even on test boxes**, and verify with
`journalctl -t hl_data_retain --since "1 hour
ago"` showing actual `starting ...` lines after the first cron tick.

**Recovery if you DO hit it** (used 2026-06-26): with hl-visor stopped,

```bash
sudo rm -rf /home/ubuntu/hl/data/replica_cmds/*
sudo find /home/ubuntu/hl/data/periodic_abci_states -name "*.rmp" -mmin +120 -delete
```

is safe — `replica_cmds` get regenerated post-restart, and
`periodic_abci_states` snapshots older than 2 hours are redundant once
the current `hl/hyperliquid_data/abci_state.rmp` exists. Don't touch
`abci_state.rmp` itself — that's the working snapshot needed for fast
restart. Then install retention per this section before starting visor.

## 14. Daily memory-threshold restart cron

Restarts hl-visor (and both publishers in sequence) if hl-node RSS exceeds
a threshold. Fires every day at 04:00 EDT (08:00 UTC), skips most days
when memory is normal.

```bash
scp overmind/studies/hl_feed/hl_node_mainnet_samples/hl_weekend_restart.sh n1:/tmp/
ssh n1 <<'EOF'
sudo install -m 755 /tmp/hl_weekend_restart.sh /usr/local/bin/hl_weekend_restart.sh
(crontab -l 2>/dev/null; echo '0 4 * * * /usr/local/bin/hl_weekend_restart.sh') | crontab -
EOF
```

The script:
- Checks hl-node `VmRSS` against threshold (default 70 GB)
- If below threshold: emails "no restart needed" and exits
- If above OR `--force`: restarts `hl-visor.service`, waits 60 s, restarts `hl-publisher-books.service` (with `--bootstrap`), then `hl-publisher-fills.service`, waits 15 s, emails summary
- Total restart wallclock: ~80-90 s. Consumers fall back to WS during, recover automatically

**Why the publisher restarts**: hl-node re-streams catch-up events to the
streaming files after restart, which would otherwise corrupt the books
publisher's accumulated state. See `hl_node_timeline.md` 2026-06-25
discovery for evidence.

**Verify:**
- `ssh n1 'crontab -l'` shows the line
- Wait for next 04:00 EDT firing → email arrives confirming "no restart needed" (when memory is low) or restart summary (when triggered)
- Test the force path: `ssh n1 '/usr/local/bin/hl_weekend_restart.sh --force'` (will actually restart!)

## 15. iptables REJECT for RFC1918 outbound peers

HL gossip RPC returns candidate peer lists that sometimes include RFC1918
private IPs (e.g., `192.168.248.143`). These are unreachable from our VPC
and waste ~5 s per attempt to time out during peer failover cascades.
Adding an iptables REJECT cuts the wait to <1 ms.

```bash
ssh n1 <<'EOF'
# Apply the rule
sudo iptables -I OUTPUT -d 192.168.0.0/16 -j REJECT --reject-with icmp-host-unreachable

# Make it persistent across reboots
echo "iptables-persistent iptables-persistent/autosave_v4 boolean true" | sudo debconf-set-selections
echo "iptables-persistent iptables-persistent/autosave_v6 boolean true" | sudo debconf-set-selections
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y -qq iptables-persistent
sudo netfilter-persistent save
EOF
```

**Safety check** before applying: confirm no legitimate traffic uses
`192.168.0.0/16`:
- n1's VPC is `172.31.0.0/16` (not in the blocked range)
- No routes to `192.168.x.x` configured
- No crontabs / scripts reference `192.168.x.x`

**Verify:**
- `sudo iptables -L OUTPUT -v -n` shows the rule
- `ping 192.168.1.1` returns "Destination Host Unreachable" in <10 ms (vs the ~5 s TCP timeout without the rule)
- `cat /etc/iptables/rules.v4` contains the REJECT rule
- `sudo systemctl is-enabled netfilter-persistent.service` returns `enabled`

**Do NOT extend to `10.0.0.0/8` or `172.16.0.0/12`** without careful
analysis — AWS-managed services use 10.x and our VPC is inside
172.16.0.0/12. See `hl_node_timeline.md` 2026-06-24 for context.

## 16. Elastic IP (EIP) — durable public IP for validator whitelist

Without an EIP, n1's public IP can change on stop/start. With a validator
operator's `reserved_peer_ips` whitelist depending on our IP, this would
break the relationship. EIP is free while attached to a running instance.

```bash
# Allocate (may need quota raise from 5 → 10 EIPs via Service Quotas console first)
EIP_RESULT=$(aws ec2 allocate-address \
  --domain vpc \
  --region ap-northeast-1 \
  --tag-specifications 'ResourceType=elastic-ip,Tags=[{Key=Name,Value=n1-feed-eip},{Key=Purpose,Value=hl-node-public-ip},{Key=Env,Value=prod}]' \
  --output json)
ALLOC_ID=$(echo "$EIP_RESULT" | jq -r .AllocationId)
EIP=$(echo "$EIP_RESULT" | jq -r .PublicIp)
echo "Allocated: $EIP (alloc $ALLOC_ID)"

# Associate (causes brief ~5-30 s peer reconnect — quiet window recommended)
aws ec2 associate-address \
  --instance-id "$INSTANCE_ID" \
  --allocation-id "$ALLOC_ID" \
  --region ap-northeast-1

# Update ~/.ssh/config on dev box
# Update Host n1 HostName to the new IP
```

**Verify:**
- `ssh n1 'curl -s https://checkip.amazonaws.com/'` returns the new EIP
- `aws ec2 describe-addresses --allocation-ids $ALLOC_ID` shows it attached
- All three services on n1 returned `active` after the brief disruption
- Sync caught up (chain block_time within 1 s of wall clock)

The EIP allocation ID is the durable identifier — record it in
`hl_node_timeline.md`. Even if the instance is terminated, the EIP can be
re-associated to a new one.

## 17a. OOM canary (between-restart safety net)

The daily restart cron (step 14) catches memory growth at 04:00 EDT.
But if hl-node memory grows faster than expected mid-day (we observed
~9 GB/hour right after the 06-25 restart), we could OOM before 04:00.
This canary runs every 30 minutes and emails if `VmRSS > 95 GB` (out of
123 GB system RAM). Rate-limited to 1 alert per 2 hours to avoid spam.

```bash
scp overmind/studies/hl_feed/hl_node_mainnet_samples/hl_oom_canary.sh n1:/tmp/
ssh n1 <<'EOF'
sudo install -m 755 /tmp/hl_oom_canary.sh /usr/local/bin/hl_oom_canary.sh
sudo mkdir -p /var/lib/hl_oom_canary
sudo chown ubuntu:ubuntu /var/lib/hl_oom_canary
(crontab -l 2>/dev/null; echo '*/30 * * * * /usr/local/bin/hl_oom_canary.sh') | crontab -
EOF
```

The script:
- Reads hl-node `VmRSS` from `/proc/<pid>/status`
- If under threshold: silent exit (no log, no email)
- If over threshold AND last alert > 2 h ago: emails with recommended `--force` action, updates state marker
- If over threshold but rate-limited: logs to journal, no email

**Verify:**
- `ssh n1 'THRESHOLD_KB=1000000 /usr/local/bin/hl_oom_canary.sh'` (test path with artificially low threshold) — sends a test email tagged "OOM CANARY: RSS ...GB exceeds 0GB"
- Reset rate-limit: `ssh n1 'sudo rm -f /var/lib/hl_oom_canary/last_alert'`
- Watch journal: `journalctl -t hl_oom_canary --since "5 min ago"`

## 17. Validator-operator IP whitelist coordination

Once the EIP is associated, share the EIP address with reliable
validator/peer operators. They add it to *their* `reserved_peer_ips`
config, which ensures their node always accepts our outbound connection
even when "full." This is the lever for reducing peer-network outlier
events from ~30-50 s to ~5 s.

Operators to approach (from HL's published root peers table):
- ASXN (`64.31.48.111`, `64.31.51.137`)
- Luganodes (`35.74.132.113`, `35.79.2.229`)
- Hypurrscan (`13.230.78.76`, `52.195.133.97`)
- Infinite Field (`52.68.71.160`, `13.114.116.44`)

**Verification once they've added us**: force a failover by blocking our
current upstream with iptables for ~30 s, watch the failover cascade in
the journal — we should connect to the whitelisting peer immediately
instead of cycling through "Peer full." Same technique as E11.
