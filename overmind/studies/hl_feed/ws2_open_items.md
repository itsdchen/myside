root cause.

### 0. Datalog + feed reconnect resilience *(PARTIAL 2026-06-13)*
The 5am EDT 2026-06-13 HL public API outage (502s for several minutes)
exposed two weaknesses; first one is fixed, second is deferred:

- **`simple_datalog` (WS mode) died entirely** at ~05:00 EDT. Root cause
  turned out to be SIGPIPE on a stale TLS write after the remote
  restart — `simple_datalog` never installed a SIGPIPE handler, default
  action terminated the process silently (no log, no dmesg). Pkmultifeed
  has done `signal(SIGPIPE, SIG_IGN)` since day one and survived the
  same outage cleanly.
  - **DONE 2026-06-13**: added `signal(SIGPIPE, SIG_IGN)` to
    simple_datalog (commit `b1825259`); also removed an unrelated dead
    `pong_count > 5 && count == 0` suicide path at line 566 in all three
    `recv_*` functions — `pong_count` was never incremented anywhere so
    the check could never fire (commit `7d0d65ac`). In prod the
    `daily-capture-hlnode.sh` / `daily-capture.sh` wrappers already
    respawn on non-zero exit, but ad-hoc / debug runs (like the
    overnight investigation) now also survive.

- **`pkmultifeed_test` (WS leg) survived** but retried every ~10s through
  the 502 storm. Watchdog (`pkmultifeed.cc:1164`) is doing its job; the
  noisy retry rate is the only thing to clean up. **DEFERRED**:
  exponential backoff on the WS reconnect path, capped at ~60 s, so we
  don't hammer HL during scheduled upgrade windows. Cosmetic — doesn't
  change time-to-recovery, just reduces log noise.

- **n1 path was unaffected** through the outage (visor + publisher kept
  running, ZMQ SUB auto-reconnect is fine).

  - **Rule 1 — no aggressive new synth at continuous resync.** If WS reports
    a level we don't already track AND it's more aggressive than our current
    inside of book (e.g., a new bid above our top bid), skip seeding it. A
    genuinely-new aggressive level would have arrived as a `new` event in
    the diffs; if it's only in WS, it's stale. Subsumes the inverted-synth
    cross-prune and stops the `crossed node/ws = 106/0` symptom.
  - **Rule 2 — delta-from-WS for already-known levels.** Same as B1 fix
    scoped to prices we already have real or prior synth at.
  - **WS keepalive ping (B-ping).** Send `{"method":"ping"}` on the
    bootstrap WS every 25 s. HL closes idle sockets at 60 s, and the
    publisher's previous unexplained stall correlated with WS-side
    silence. Mirrors `pymultifeed.py:hl_ping`. **Port note:** any C++/Rust
    port must recreate this keepalive loop — see "Port to C++ / Rust".
  - **B4 — fills emit two book-diff events (update→0 then remove).**
    Verified by oid cross-reference: a fully-filled order produces both
    `{"update":{...,"newSz":"0.0"}}` and `"remove"` in the same block.
    The publisher handles the first correctly via `update_known(rm)`;
    the second arrives as `is_known=False` and falls through to
    `_synth_estimate_remove`, which post-catch-up is a no-op. Confirmed
    not a contributing factor to the residual mismatches and left
    in place.
  - **Catch-up criterion: time-indexed history of recent emit-time top-5s.**
    Was: compare WS's top-5 to our current real top-5, fail if any
    (px,sz,n) differs. Problem: WS samples *between* our blocks, so its
    state matches whichever block was current at WS's sample time —
    not whichever happens to be current at the moment of the check.
    Fix: `L3Book` keeps a 60-entry deque of `(event_time_ms, top5)`; on
    WS arrival, look up the entry whose `event_time ≤ ws.data.time` and
    compare *that*. Catch-up time dropped from "never within 5 min" to
    "~15 s after start". Also added WS-lag telemetry (`recv − time`) so
    future runs can detect WS-side degradation.
  - **Numeric size comparison.** Both the catch-up criterion and the
    offline comparator were doing strict string equality on `sz`, but
    `format_qty` strips trailing zeros (`"2"`) while WS emits them
    (`"2.0"`). Identical values, unequal strings. Fix: compare `float(.)`.
    Lifted post-catch-up top-5 px+sz+n match from 52 % to 86 % and made
    catch-up reliable (was occasionally getting stuck on benign formatting
    differences). The comparator script
    `~/scratch/hl_publisher_debug_20260610/time_aligned_compare.py` got
    the same fix.

  **Residual behavior** (not a bug, documenting reality): WS occasionally
  reports orders that aren't in `node_raw_book_diffs` at all — proven by
  offline replay matching emit-time state for 2,398 consecutive snapshots
  at `A@28755` with zero divergence from the publisher, while WS persistently
  reported +1 order / +0.4142 sz at that price for ~3 s. Likely
  trigger / TWAP / iceberg / HIP-3-specific orders not exposed in the
  raw-diff stream. For our node-feed use case the diffs are canonical;
  no further action needed.

  All debug artifacts (filtered diffs hours 1-4, watch_emit log, recorder
  captures, replay scripts, mismatch-duration analyzer) live in
  `~/scratch/hl_publisher_debug_20260610/` with README.

  Two changes targeting long-term memory growth on the publisher.
  - `--l3-max-levels-per-side` flag (default 100, well above the
    wire emit cap of 40). `L3Book::trim_to(cap)` runs at the end of
    `snapshot_l2_for_emit` (once per block per sym), drops the

    state. Subsequent update/remove events for those oids fall
    through the existing unknown-oid path (a no-op post-catch-up).
    Tally surfaced as `l3_trimmed=N` in the per-rotation log line.

    `OnCalendar=Sun *-*-* 02:00:00` (Sunday 2am ET, n1 is on
    US/Eastern). Chosen to land safely after HL's own network
    restart window (roughly Saturday ~04:00 ET), so chain state has
    had ~22h to settle before our publishers re-bootstrap. The oneshot
    service it triggers runs `systemctl restart
    hl-publisher-books.service hl-publisher-fills.service`. The
    `--bootstrap` path on books wipes any L3 drift accumulated
    from missed deep-level events; consumers fall back to HL WS
    for the ~15s catch-up window via their health FSM. The L3
    trim already bounds memory growth in-process, so weekly is
    enough cadence — the restart's only remaining jobs are
    drift-wipe and binary upgrade pickup.
